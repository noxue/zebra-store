# 钱包支付的转换卡退款

基线为640149f，与主分支合并提交a1565eb的代码树一致。该补丁已实现；本地完整验证及固定Linux候选构建与生产部署分开记录，不能把本地通过视为已经上线。

## 触发与行为

全额钱包支付的转换卡能够购买和交付，但此前买家只看到contact_support，管理员退钱包又被卡密屏障拒绝。问题在于原路/人工通道退款依赖在线支付渠道，钱包通道没有对应的持久转换卡退款流程。

现在，全额钱包付款可沿原支付凭证申请整单退款：先通过转换器prepare冻结整批未用卡，再在一次本地事务中返还原用户钱包、写退款记录、更新父子订单及冲回收益，最后confirm作废卡密。买家仍使用原退款路径；管理员仍使用原refund-to-wallet路径。线上或混合支付不能改走钱包，已交付转换卡的部分退款、子单单独退款和不明付款凭证仍明确拒绝。

非转换商品原有钱包退款及在线支付原路退款保持原行为。不通过解绑、改订单状态、伪造网关支付或直接改余额绕过屏障。

## 持久与并发

- 复用gateway_refund_attempts账本。WR前缀和channel_id=0标识原钱包付款的退款，绑定真实的单一success钱包支付记录；没有新增外部网关调用、表结构或生产数据迁移。
- 统一先取得父单及子单锁，再锁成功支付。初次意图落库前在锁内重查整单金额、原钱包实付、币种和无历史退款；实际入账事务再核对付款凭证与剩余额度。
- preparing只允许准备；确认prepare后，条件更新成pending，才可原子返款。重复请求、并发请求、进程中断或丢响应复用原WR和退款记录，不重复入账。
- prepare失败后必须先竞争取得wallet_canceling状态，才能取消锁卡。另一工作者已进入pending或已返款时不能取消。取消响应不明保留原意图、金额及卡锁，按原编号恢复；取消完成后才记failed。
- pending表示此前已获得准备确认。返款事务失败时保持pending及卡锁；后台恢复原事务。succeeded但card_confirmed=false时，钱已经退回，只继续卡密确认，不再次返款。
- 退款窗口在初次接受WR前检查。已接受的意图在停机恢复时继续完成，即使期间越过窗口；账本时间采用实际返款时刻。新申请不能绕过窗口，也不能更换金额、币种、用户、批次或退费选项。
- 普通及管理员强制路径继续受原采购未决屏障约束。旧卡和旧订单不因商品下架或新发行权限撤销而被覆盖。

## 接口与界面

原请求字段及成功响应order/transaction保留，管理员钱包退款响应增加refund_state和attempt。成功返款但卡确认未完成时为syncing；前端分别提示款项成功和卡密同步，不显示全部完成。相同成功请求的transaction可为null，表示读取原退款而非第二笔入账。

买家退款响应仍为status/refund_no，不暴露网关配置或卡密。全额钱包付款的自动退款优先选钱包操作；管理员在线支付订单不显示退余额按钮。
