# 执行计划

## 项目目标

构建一套可独立部署的数字商品交易系统：

- **backend**：Rust + axum + sea-orm，默认 SQLite，改配置即可切换 MySQL / PostgreSQL
- **storefront**：用户商店前台（Vue3 + TSX，二次元风格）
- **admin**：管理后台（Vue3 + TSX，二次元风格），站点名 / Logo / 主题等可在后台自定义

系统提供稳定的 API 契约（路径、字段、信封、错误码）、完整的商店与管理功能，
并通过独立适配器兼容常用发卡站协议。页面与交互以 `docs/reference/*-spec.md` 为验收依据。

## 前期调研结论

- 兼容性参考服务已在本地跑通，并写入了示例数据
  （分类、商品、SKU、卡密、支付渠道、Banner、文章、会员等级、优惠券、活动价、礼品卡、用户、订单）
- 截图：用户前台 28 页（游客 18、会员 10）、管理后台 58 页、暗色 2 页，共 88 张，存于 `docs/reference/screenshots/`
- 三份规格文档：后端（约 60 张表、约 330 个路由、业务流程、10 种支付网关、20 个设置 key、16 类后台任务）、前台、后台

## 关键设计决策

| 问题 | 决策 | 理由 |
|---|---|---|
| 分层 | 7 个 crate：shared / domain / app / infra / migration / api / server | 依赖方向由 Cargo 强制，并由架构测试验证 |
| 多数据库 | sea-orm + sqlx 三个驱动特性全开；迁移只用 SchemaBuilder | 运行时按 URL scheme 选择驱动，只改配置即可切换 |
| 任务队列 | **基于数据库的任务表 + tokio worker** | 默认无需 Redis，减少部署依赖 |
| 缓存 / 限流 | 默认进程内（moka + 自研令牌桶），可选开启 Redis | 单机开箱即用，也支持扩展部署 |
| RBAC | casbin-rs（keyMatch2 + role 继承），策略存 `casbin_rule` 表 | 权限 key 统一为 `METHOD:/admin/...` |
| 金额 | rust_decimal，序列化为两位小数字符串 | 避免浮点误差并保持接口格式稳定 |
| 加密 | AES-256-GCM（key = sha256(secret)，hex(nonce‖ct)）、HMAC-SHA256 签名 | 支持安全存储及供应商协议签名 |
| 前端 | 两个独立 Vite 项目，TSX；Tailwind v4 + 自研二次元组件库 | 按要求一共三个项目，前端之间不共享包 |
| 主题可配置 | `site_config.brand`（名称 / Logo / 图标）+ `site_config.theme`（主色、强调色、背景图、看板娘图、动效开关） | 支持后台完整配置品牌和视觉风格 |

### 支付渠道与支付方式前台呈现

- 管理后台允许一个渠道配置多个实际支付方式；Huifu 的支付宝/微信应可在同一套商户凭证下启用，Epusdt 等聚合通道按其实际支持的币种/链展示。
- 前台将所有启用渠道展开为“支付方式”选项。渠道名默认隐藏：例如 Huifu 的微信/支付宝和 Epusdt 的多条 USDT 链作为并列支付类型展示，即使它们来自不同渠道也不额外展示渠道名。
- 只有同一种支付方式由多个渠道同时提供时，才在这个重名方式上显示渠道名以区分（例如易支付微信与汇付微信）；其他不重名方式仍只显示支付类型。
- 可选项只有一个时自动选中并隐藏选择控件；有多个不同支付类型时直接并列显示。支付创建请求必须携带所选类型，后端验证该类型确实属于该渠道并将其写入本笔支付记录，避免用户选了微信却按支付宝发起。
- 支付方式使用可识别的品牌/币种图标（支付宝、微信、USDT/其他币种）；发生同名方式冲突时同时保留渠道名称。图标资源应随项目版本分发，避免依赖临时远程图片地址。
- 回调/通知 URL 的推测与表单预填在前端完成，使用可靠的站点 origin 推导；编辑已配置值时保留管理员输入。

支付方式选择回归至少覆盖：单渠道单方式、单渠道多方式、多个渠道提供不同方式、不同渠道提供同名方式，以及混合情形（只给重名项附加渠道名）。另验证方式和渠道 ID 配对提交、禁用/金额限额、旧渠道配置兼容、支付结果显示正确类型、币种图标与品牌图标可加载。

### 汇付原路退款与 AI Top-up 卡密防滥用（2026-10-14）

目标：验证汇付聚合正扫自动退款，并把能力放入独立 Rust SDK 和 Store；线上选择一笔已实付订单做小额原路退款。任何已交付给 AI Top-up 的卡密，退款流程必须防止用户在退款同时提交充值，并在退款成功后明确标记“因退款失效”、释放仍可释放的上游绑定。

执行顺序与验收门槛：

1. **汇付证据**：用上级 Go SDK 项目对已实付订单查单，固定退款流水号后只提交一次退款；用官方退款查询确认最终状态与金额。记录可复核的订单号和退款流水号，不记录密钥或卡密。
2. **SDK 与 Store**：独立 `huifu-pay` crate 实现聚合正扫退款及退款查询，复用签名、验签、金额和日期校验；Store 网关改用 SDK。退款请求超时或状态不明时查询同一流水号，禁止用新流水号盲重试；本地退款记录只在汇付最终成功后落库。
   Store 必须按渠道能力判断：明确支持自动退款的渠道才调用网关；不支持自动退款或不支持目标金额/部分退款的渠道不发起网关退款。买家直接联系客服申请人工退款。客服处理仍执行下述同一套资格、锁卡、失效原因、解绑定和审计流程；未确认实际退款前保持待处理锁定，不得先把资金退款记录记成已完成。
   人工渠道后台分两步：先准备人工退款并锁定卡密，客服核实已原路转回后填写外部退款流水号确认；确认接口按准备记录幂等地落一笔资金退款、同步卡密失效与解绑定。准备未确认期间阻止发货、自动/钱包/旧手动退款；确认同步失败由持久重试补偿。
   买家自助申请与管理员后台点击“退款”共用一条退款服务和同一幂等状态机。管理员点击支持自动退款的渠道时也直接发起网关原路退款；不支持的渠道只在客服确认线下原路退回后完成后台人工退款。管理员入口不得绕开资格检查、转换器准备/确认或重复退款限额。
3. **可退资格**：只允许已付款、金额和原支付归属核对一致、未超过可退余额与期限的订单。涉及卡密时，先确定交付来源及每张系统卡的状态。已使用、充值处理中、充值结果未知、上游绑定状态不明、转换器失联或状态无法证明的卡密不得自动退款；管理员收到明确的人工核查原因。部分退款必须能对应可撤销的具体卡密，禁止金额与卡密集合不一致。
4. **跨系统并发屏障**：扩展通用卡密转换器协议，在 AI Top-up 中增加经专用 Token 鉴权、按订单号幂等的退款准备/确认/撤销接口。准备阶段在数据库事务中锁定系统卡和相关任务，确认未使用后标记 `refund_pending`，此状态使验证和充值提交都拒绝；Store 只有拿到全部卡的准备成功才调用汇付。汇付失败可撤销准备；结果未知维持锁定并通过同一退款流水号对账。成功后确认阶段标记 `refund_invalidated`、审计原因 `payment_refund`，并在确认没有进行中任务及其他有效绑定后释放上游绑定；失败或超时由持久任务重试，直到双方状态一致。
5. **线上验收**：先只读核对正式店铺订单、支付记录、交付及 AI Top-up 绑定状态，优先使用已实付且未交付/未使用的最小金额订单。更新并部署两个系统后，经 Store 原路退款接口提交一次，查询汇付最终结果，并复查 Store 退款记录、订单状态、AI Top-up 失效原因与上游绑定释放。任何资格不明时不发起真实退款。
   买家订单详情应明确说明“如果买错或不再需要，可申请退款，款项原路返回”。支持该笔金额自动退款的支付渠道提供自助申请入口，服务端受理后先执行资格校验和卡密锁定，再发起原路退款；不支持自动退款的渠道显示“联系客服申请人工退款”及可用联系方式，不创建自助退款单。页面只按真实资金与卡密状态展示待处理、退款中、成功或需人工核查，不把申请成功误写成到账成功。
6. **边界测试**：至少覆盖已使用、处理中、结果未知、未绑定、多个绑定、部分退款、多卡批量、重复请求、并发退款与充值、退款提交超时、查询仍处理中、汇付失败、确认回调失败与重试、跨日重试、签名/Token 错误、金额/商户/订单不匹配、AI Top-up 失联及部署版本不兼容；同时覆盖渠道不支持自动退款、不支持部分金额退款、人工退款确认前后和人工操作中断。Go、Rust SDK、Store API 和 AI Top-up 的自动化测试及各仓库既有格式/lint/测试门禁均通过后勾选相应 TODO。

## M16 卡密转换器：跨系统设计与验收

此功能由 Zebra Store 和外部卡密程序（当前为 ai-top-up）共同实现。完整协议见 `docs/protocol/card-converter.md`，执行项和完成状态见 `docs/TODO.md` 的 M16。后续新增转换程序应实现同一协议，不在 Zebra Store 中写针对某个程序的业务分支。

### 配置方式

- 一个第三方程序配置一条可复用的转换器连接；多个商品和 SKU 可以复用同一连接，通过每个商品/SKU 单独配置的 extra 字段和条件规则区分业务。
- 商品/SKU 直接绑定转换器；管理后台提供自定义 extra 字段表单和条件规则，高级模式可编辑同一份 JSON。订单、站点、商品、SKU、数量等已有信息仅作为 extra 可选变量，不自动随请求发送；管理员按转换器要求自行定义 extra 字段名和类型，并可预览请求、复制已有配置。
- 配置商品转换器即启用转换。适用于上游采购后取得原始卡密，也适用于管理员手动导入的上游卡密；手动导入时不要求额外标记来源。没有绑定转换器时维持原交付流程。
- 商品/SKU 选择器显示本地商品及已知上游来源，作为管理员判断绑定对象的辅助信息；来源本身不是是否执行转换的开关。
- 第三方程序必须为 Zebra Store 单独创建权限受限、可撤销轮换的认证 Token，不得复用管理员或高权限 API 凭证。

### 失败与恢复

- 上游已确认采购成功后，先持久化原始交付为内部待转换数据，再调用转换器。转换失败只重试转换，不得重新向上游采购，避免重复扣款和重复进货。
- 同一订单的转换重试使用相同订单号及相同请求。转换失败期间订单保持处理中，待转换原文不能出现在买家查单、邮件、Webhook、下游 API 或其他外部响应中。
- 转换器恢复健康后，健康恢复事件唤醒对应待处理任务；任务重用已保存的上游卡密和订单号。全部转换成功后才写入正式交付、完成订单并向用户提供系统生成的卡密及通知。
- 持续失败、类型/数量不匹配或不可重试错误进入可观测的人工处理状态。管理员修复连接或绑定后，应能重试原任务，不重新采购、不重复扣库存；转换健康状态、失败原因、待处理数量和恢复结果进入日志、通知及管理首页。

### 验收范围

- 两个项目分别验证受限认证和三字段转换请求；验证 extra 配置、条件规则、来源展示、无转换器时兼容旧流程。
- 覆盖卡密数量多/少/空、类型不匹配、部分失败、重复请求、超时/断连/限流/服务端错误、转换器不可用后恢复、进程重启后的待处理恢复，以及修复配置后的人工重试。
- 特别确认“上游购买成功、转换失败、稍后恢复”的全链路只采购一次；正式卡密在转换成功前不可见，恢复成功后能在原订单中查到并通知买家。
- 本地验证通过后分别发布并部署 Zebra Store 与转换器程序；把认证要求、转换请求/响应、幂等与错误恢复规则写入开发者文档并验证线上接口。
