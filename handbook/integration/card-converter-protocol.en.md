# Card Converter HTTP Protocol

This document defines the HTTP contract between Zebra Store and an independently deployed card converter. A converter validates or imports cards received from an upstream supplier and returns cards generated by its own system. Zebra Store binds products to converters and does not hard-code converter-specific fields. There is currently one protocol; its version appears only in the `/v1/` URL path, not in request or response JSON.

## Authentication and security

Create a dedicated token for Zebra Store with only the permissions needed to run health checks and exchange cards. Never use an administrator token, a primary API token, or a credential with account-management or payment permissions. The token must be independently revocable and rotatable. Production endpoints must use HTTPS. Zebra Store encrypts saved credentials; responses, logs, screenshots, and errors must not reveal tokens or full card values.

Send `Authorization: Bearer <dedicated-token>`. The converter uses request-body `order_no` as its idempotency identity. It must persist results: the same order number and request returns the original result; a different request for the same order number returns `409 idempotency_conflict`.

## Endpoints

A converter implements `POST /integration/v1/exchanges` and `GET /health`. All business field names and values are configured in per-product `extra` and interpreted by the converter. No type discovery endpoint is required.

## Exchange cards

`POST /integration/v1/exchanges`

```http
Authorization: Bearer <converter-token>
Content-Type: application/json
```

```json
{
  "order_no": "ZS202609300001",
  "items": [{"index": 0, "upstream_card": "UPSTREAM-CARD-1"}, {"index": 1, "upstream_card": "UPSTREAM-CARD-2"}],
  "extra": {"region": "us", "merchant_order": "ZS202609300001", "custom_flag": true}
}
```

The successful response must contain exactly one non-empty output for every input index. Output order may differ, but an index cannot be missing, duplicated, or added. A type or output-count mismatch must reject the entire request; partial success is not allowed. Zebra Store saves a fulfillment and completes the order only after validating the complete response.

```json
{
  "items": [
    {"index": 0, "card": "SYSTEM-CARD-1"},
    {"index": 1, "card": "SYSTEM-CARD-2"}
  ]
}
```

Do not return an `upstream_card` unchanged as a successful output unless the converter has explicitly validated and accepted it as a usable system card. Responses are UTF-8 JSON, limited to 1 MiB by default, and should finish within 15 seconds. Asynchronous jobs are not currently defined.

## Errors and retries

Use this JSON shape and do not echo credentials or cards:

```json
{"error":{"code":"type_mismatch","message":"Card type does not match the configured type","retryable":false}}
```

| HTTP | code | Retryable | Meaning |
|---|---|---:|---|
| 400 | `invalid_request` | No | Invalid request shape or fields |
| 401/403 | `unauthorized` | No | Invalid token or insufficient permission |
| 409 | `idempotency_conflict` | No | Key reused with a different request |
| 422 | `type_mismatch` / `card_rejected` | No | Type mismatch or rejected upstream card |
| 429 | `rate_limited` | Yes | Rate limit; may include `Retry-After` |
| 5xx | `temporarily_unavailable` | Yes | Temporary service failure |

Timeouts, connection failures, 429, and 5xx can be retried with the **same order number**. Zebra Store does not follow redirects. Configure a public HTTPS host; loopback, private-network, and cloud-metadata addresses are refused.

## Delivery recovery

After an upstream purchase succeeds, Zebra Store persists the raw supplier delivery internally before calling the converter. If conversion fails, the order remains processing and retries repeat only the conversion with the same order number and request. The supplier purchase is never submitted again. When converter health recovers, held jobs are resumed. The buyer receives no final fulfillment or notification until every card converts successfully. Permanent type errors or exhausted retries wait for admin handling; after fixing the binding, an admin can retry the held conversion. Raw supplier cards are never returned by buyer order lookup, downstream supply APIs, email, or webhooks.

Local-stock products use the same delivery boundary. Zebra Store reserves and marks the selected cards used, then creates an empty pending fulfillment before calling the converter. Retries reuse the same cards and order number without consuming more stock. Only a complete successful conversion fills the buyer-visible fulfillment, completes the order, and sends a notification. The pending empty fulfillment does not expose raw cards.

Admin manual fulfillment follows a product binding as well: when the admin enters one card per line with the exact order quantity, Zebra Store calls the converter before saving the delivery. A failure leaves the fulfillment unsaved; retrying the same input uses the same order number and returns the same result. Supplier messages that require human handling are not treated as cards.

## Product bindings and context

One converter connection represents one third-party program and can serve multiple products and SKUs. Bind each product or SKU to a discovered type and configure that product's type-specific fields and `extra`. The product selector identifies local products and their known upstream mapping; importing stock does not require recording the source of each card. A configured binding runs for that product's purchase delivery; an unbound product keeps its existing delivery path.

The request body has exactly three top-level fields: `order_no`, upstream card `items`, and configured `extra`. Site, product, and SKU details are not sent automatically. `extra` keys are chosen by the administrator to meet the converter’s requirements; Zebra Store does not fix keys within `extra`, such as category or provider. Values accept JSON constants and these context placeholders: `&#123;&#123;order.order_no&#125;&#125;`, `&#123;&#123;order.quantity&#125;&#125;`, `&#123;&#123;order.total_amount&#125;&#125;`, `&#123;&#123;site.domain&#125;&#125;`, `&#123;&#123;site.name&#125;&#125;`, `&#123;&#123;product.id&#125;&#125;`, `&#123;&#123;product.title&#125;&#125;`, `&#123;&#123;sku.id&#125;&#125;`, `&#123;&#123;sku.specifications&#125;&#125;`, `&#123;&#123;source.id&#125;&#125;`, `&#123;&#123;source.name&#125;&#125;`, and `&#123;&#123;source.protocol&#125;&#125;`. Form mode offers field controls and a variable picker; advanced mode edits the complete JSON object. Both modes synchronize. Before saving, advanced text must parse as a JSON object, and rule structure and variable paths are checked. Placeholders are stored as JSON strings, replaced in memory with order values at delivery, and then serialized into the request. Templates do not execute arbitrary code. Email addresses and phone numbers are omitted by default. The admin UI previews the request structure and lets administrators edit or copy saved bindings.

## AI Top-up example

AI Top-up provides an implementation of this protocol at:

- `POST /integration/v1/exchanges`

Set a dedicated `ZEBRA_STORE_TOKEN`; do not use `ADMIN_TOKEN` for converter requests.

```json
{
  "order_no": "ZS202609300001",
  "extra": {"category": "new_activation_go", "provider": "p1"},
  "order_no": "ZS202609300001",
  "items": [{"index": 0, "upstream_card": "UPSTREAM-CARD-1"}]
}
```

Send `X-Integration-Token: <ZEBRA_STORE_TOKEN>` or `Authorization: Bearer <ZEBRA_STORE_TOKEN>`. A successful response contains `items: [{"index":0,"card":"...","type_id":"...","provider":"p1"}]`. AI Top-up validates each card's actual product type against `extra.category` and validates the entire input before importing supplier cards and binding generated system cards in one database transaction. Card indexes must be contiguous from zero; a type mismatch rejects the whole request. Repeating the same request with the same order number returns the original cards; using that order number with a different request returns HTTP 409. Configure the category in `extra` for each product.

AI Top-up specifically requires `extra.category` to be a supported category and `extra.provider` to be `p1` or `p2`. Zebra Store does not reserve these names for other converters; administrators choose keys according to each converter. Missing or invalid values reject the batch.

## Conditional extra values

In form mode, switch any field to a conditional rule. Add ordered cases using source, order, or card variables; select equality, numeric comparison, regex match, or their negative forms; then choose a literal or variable result. The first matching case wins, followed by a required default result. A card regex matches only when every card in the batch matches. The actual upstream connection provides `source.id`, `source.name`, and `source.protocol`; local stock has no source and falls through to the default. The advanced JSON editor stores the same `$zs_rule` structure and round trips to the form. Rules are evaluated by Store before sending; the converter receives ordinary JSON. Prefer stable `source.id` over a renameable source name.
