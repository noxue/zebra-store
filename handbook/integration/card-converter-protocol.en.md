# Card Converter HTTP Protocol v1

This document defines the HTTP contract between Zebra Store and an independently deployed card converter. A converter validates or imports cards received from an upstream supplier and returns cards generated by its own system. Zebra Store maps products to converter-declared types and does not hard-code business types.

## Authentication and security

Create a dedicated token for Zebra Store with only the permissions needed to read converter types, run health checks, and exchange cards. Never use an administrator token, a primary API token, or a credential with account-management or payment permissions. The token must be independently revocable and rotatable. Production endpoints must use HTTPS. Zebra Store encrypts saved credentials; responses, logs, screenshots, and errors must not reveal tokens or full card values.

Send `Authorization: Bearer <dedicated-token>`. Exchange requests also include an `Idempotency-Key` that remains stable and unique for the Zebra Store order line. The converter must persist idempotent results: the same key and request returns the original result; reusing a key with a different request returns `409 idempotency_conflict`.

## Discover types

`GET /integration/v1/types`

```http
Authorization: Bearer <converter-token>
Accept: application/json
```

```json
{
  "protocol_version": "1",
  "types": [
    {
      "id": "new_activation_go",
      "name": "New Go activation",
      "description": "Optional description",
      "fields": [
        {"key": "region", "label": "Region", "required": true, "kind": "select", "options": ["us", "eu"]},
        {"key": "campaign", "label": "Campaign", "required": false, "kind": "text"}
      ]
    }
  ]
}
```

`id` is the converter's stable type identifier and must not change when its display name changes. Zebra Store does not infer or hard-code these values. `fields` is optional; when provided, Zebra Store generates a parameter form. Supported kinds are `text`, `number`, `boolean`, and `select`. Required fields are checked when saving a binding and before placing an order. Type discovery is required before product bindings can be configured. An optional `GET /health` endpoint can report health; if it is absent, Zebra Store checks connectivity through type discovery.

## Exchange cards

`POST /integration/v1/exchanges`

```http
Authorization: Bearer <converter-token>
Idempotency-Key: order-<opaque-id>-item-<index>
Content-Type: application/json
```

```json
{
  "protocol_version": "1",
  "type_id": "new_activation_go",
  "order": {"order_no": "ZS202609300001", "quantity": 2, "currency": "CNY"},
  "site": {"domain": "store.example.com", "name": "Example Store"},
  "product": {"id": 12, "slug": "activation", "title": "New activation", "variables": {"region": "us"}},
  "sku": {"id": 34, "code": "go-us", "specifications": {"region": "US"}},
  "items": [{"index": 0, "upstream_card": "UPSTREAM-CARD-1"}],
  "extra": {"merchant": "store-a", "custom_flag": true}
}
```

The successful response must contain exactly one non-empty output for every input index. Output order may differ, but an index cannot be missing, duplicated, or added. A type or quantity mismatch must reject the entire request; partial success is not allowed. Zebra Store saves a fulfillment and completes the order only after validating the complete response.

```json
{
  "protocol_version": "1",
  "items": [
    {"index": 0, "card": "SYSTEM-CARD-1"},
    {"index": 1, "card": "SYSTEM-CARD-2"}
  ]
}
```

Do not return an `upstream_card` unchanged as a successful output unless the converter has explicitly validated and accepted it as a usable system card. Responses are UTF-8 JSON, limited to 1 MiB by default, and should finish within 15 seconds. Asynchronous jobs are not defined in v1.

## Errors and retries

Use this JSON shape and do not echo credentials or cards:

```json
{"error":{"code":"type_mismatch","message":"Card type does not match the configured type","retryable":false}}
```

| HTTP | code | Retryable | Meaning |
|---|---|---:|---|
| 400 | `invalid_request` | No | Invalid request shape or fields |
| 401/403 | `unauthorized` | No | Invalid token or insufficient permission |
| 409 | `idempotency_conflict` | No | Key reused with a different request |
| 422 | `type_mismatch` / `card_rejected` | No | Type mismatch or rejected upstream card |
| 429 | `rate_limited` | Yes | Rate limit; may include `Retry-After` |
| 5xx | `temporarily_unavailable` | Yes | Temporary service failure |

Timeouts, connection failures, 429, and 5xx can be retried with the **same idempotency key**. Zebra Store does not follow redirects. Configure a public HTTPS host; loopback, private-network, and cloud-metadata addresses are refused.

## Delivery recovery

After an upstream purchase succeeds, Zebra Store persists the raw supplier delivery internally before calling the converter. If conversion fails, the order remains processing and retries repeat only the conversion with the same key and request. The supplier purchase is never submitted again. When converter health recovers, held jobs are resumed. The buyer receives no final fulfillment or notification until every card converts successfully. Permanent type errors or exhausted retries wait for admin handling; after fixing the binding, an admin can retry the held conversion. Raw supplier cards are never returned by buyer order lookup, downstream supply APIs, email, or webhooks.

Local-stock products use the same delivery boundary. Zebra Store reserves and marks the selected cards used, then creates an empty pending fulfillment before calling the converter. Retries reuse the same cards and idempotency key without consuming more stock. Only a complete successful conversion fills the buyer-visible fulfillment, completes the order, and sends a notification. The pending empty fulfillment does not expose raw cards.

Admin manual fulfillment follows a product binding as well: when the admin enters one card per line with the exact order quantity, Zebra Store calls the converter before saving the delivery. A failure leaves the fulfillment unsaved; retrying the same input uses the stable idempotency key and returns the same result. Supplier messages that require human handling are not treated as cards.

## Product bindings and context

One converter connection represents one third-party program and can serve multiple products and SKUs. Bind each product or SKU to a discovered type and configure that product's type-specific fields and `extra`. The product selector identifies local products and their known upstream mapping; importing stock does not require recording the source of each card. A configured binding runs for that product's purchase delivery; an unbound product keeps its existing delivery path.

Zebra Store supplies the order number, quantity, currency, trusted site configuration, product and SKU snapshots, and the upstream cards to convert. `extra` can contain constants and restricted variables such as `&#123;&#123;site.domain&#125;&#125;`, `&#123;&#123;product.title&#125;&#125;`, and `&#123;&#123;product.variables.region&#125;&#125;`. Templates substitute values only; they do not execute code. Email addresses and phone numbers are omitted by default and are sent only when explicitly selected. The admin UI should preview the request and allow saved bindings to be copied.

## AI Top-up example

AI Top-up provides an implementation of this protocol at:

- `GET /integration/v1/types`
- `POST /integration/v1/exchanges`

Set a dedicated `ZEBRA_STORE_TOKEN`; do not use `ADMIN_TOKEN` for converter requests.

```json
{
  "protocol_version": "1",
  "idempotency_key": "ZS202609300001:0",
  "type_id": "new_activation_go",
  "order": {"order_no": "ZS202609300001", "quantity": 1, "currency": "CNY"},
  "site": {"domain": "store.example.com", "name": "Example Store"},
  "product": {"id": 12, "slug": "activation", "title": "New activation", "variables": {"region": "us"}},
  "sku": {"id": 34, "code": "go-us", "specifications": {"region": "US"}},
  "extra": {"region": "us"},
  "items": [{"index": 0, "upstream_card": "P1-...", "provider": "p1"}]
}
```

Send `X-Integration-Token: <ZEBRA_STORE_TOKEN>` or `Authorization: Bearer <ZEBRA_STORE_TOKEN>`. A successful response contains `protocol_version` and `items: [{"index":0,"card":"...","type_id":"...","provider":"p1"}]`. AI Top-up validates each card's actual product type and validates the entire input before importing supplier cards and binding generated system cards in one database transaction. Quantity and sequential indexes must match; a type mismatch rejects the whole request. Repeating the same request with the same idempotency key returns the original cards; using that key with a different request returns HTTP 409. Read the dynamically published type list before configuring a binding.
