# 卡密转换器

**默认不用配置转换器。**如果导入的卡密本来就能直接给买家使用，请到[卡密导入](../admin/card-secrets)按普通流程导入。转换器只适合“上游原始卡密不能直接给买家，必须交给自己的程序验证或导入，再返回自有系统卡密”的场景。一个连接代表一个第三方程序，可以被多个商品和 SKU 使用；没有绑定转换器的商品继续原样发货。

## 配置转换程序

在后台打开 **对接管理 → 卡密转换器**，添加程序名称、公开 HTTPS 地址和专用认证 Token。这个 Token 应只允许健康探测和执行卡密转换，不要填写管理员或高权限 API Token。保存后运行连接测试。

转换端需要实现健康探测和转换请求。开发前请阅读[卡密转换器协议](./card-converter-protocol)。协议内有请求/响应样例、错误码、变量、数量校验、认证和幂等要求。

## 绑定商品和转换器

在同一个页面的商品绑定区域选择商品/SKU 和转换程序。选择器会显示本地商品或其上游映射来源，方便管理员核对。根据转换程序的接口要求自行添加 `extra` 字段，可配置常量和受限变量，例如 <code v-pre>{{site.domain}}</code>、<code v-pre>{{product.title}}</code>。邮箱、手机号等个人信息默认不会传递。

转换请求的 JSON 主体顶层只有订单号 `order_no`、上游卡密列表 `items` 和 `extra`；订单号同时用于幂等。站点、商品、SKU 的字段不会自动附带，只有配置进 `extra` 的值才会发送。`extra` 的字段名由管理员依据转换程序的接口要求自行添加，不由 Zebra Store 固定。

### 编辑 `extra`

默认的**普通模式**可直接添加字段，按文本、数字、布尔值或 JSON 值编辑。文本字段可用“插入订单变量”追加 <code v-pre>{{变量路径}}</code> 占位符，例如 <code v-pre>{{order.order_no}}</code>。可选择订单号、数量、金额、站点域名与名称、商品 ID 与名称、SKU ID 与规格，以及实际采购上游的 ID、名称和协议。占位符保存在商品绑定中，实际交付时才用该订单的数据替换；含引号等字符的替换值仍作为 JSON 字符串安全序列化。

点**高级 JSON**可以直接编辑完整的 `extra` 对象，例如：

```json
{
  "provider": "p2",
  "merchant_order": "{{order.order_no}}",
  "notify": true
}
```

最外层必须是 JSON 对象，字符串中的占位符必须放在引号内。JSON 格式错误时会保留当前编辑内容，但不能切回普通模式或保存。格式正确后切回普通模式，表单会同步显示所有顶层字段；嵌套对象和数组显示为可编辑的 JSON 字段。保存前还会检查 JSON 结构、条件规则和变量路径。

### 条件规则

字段类型选择“条件规则”后，可点击添加多条“如果”条件，选择来源名称、订单数量、卡密或卡密导入备注等变量，再选等于、大小比较或正则匹配。每条条件的输出可以是固定值或变量；最下方配置“否则输出”。按从上到下的顺序，第一条命中即生效。卡密和“卡密导入备注（每张均匹配）”规则要求本订单所有卡密都匹配。切换到高级 JSON 编辑后再回来，规则仍可在表单中继续修改。规则只保存在 Store，实际请求中的 `extra` 是求值后的普通 JSON。

仅当转换程序是 AI Top-up 时，在 `extra.category` 中填写套餐类型，在 `extra.provider` 中填写 `p1`、`p2` 或 `p3`；也可以给 `provider` 设置来源名称或卡密格式条件。Zebra Store 不解析这两个值。已有绑定也需补全这两个字段，新转换请求才会被 AI Top-up 接受。

在 **商品 → 卡密导入** 中，批量录入和 CSV 导入都可以填写“导入来源 / 备注”。该备注关联本批每张卡密。本地库存发货时，转换器规则可用“卡密导入备注（每张均匹配）”按渠道选择 `extra.provider` 等值；同一订单多张卡密来自不同备注或有空备注时，这个条件不会命中。若所有卡密备注一致，还能使用 <code v-pre>{{card.note}}</code> 将它写入 `extra`；混合备注订单使用此占位符会停止转换并保留订单待处理，以免把卡密发往错误渠道。建议同一商品的导入批次使用稳定、统一的渠道标识。上游采购的来源仍使用 `source.*` 变量。

### 同一商品混用 AI Top-up P1 导入与 P2 采购

已绑定转换器的上游商品可以同时使用本地导入的 P1 卡密和原有 P2 采购。导入 P1 卡密时，**批次备注准确填写小写 `p1`**，并选择该商品对应的 SKU。下单时若这类本地卡密足够覆盖整笔购买，系统优先锁定 P1 卡密并按本地自动发货；否则整笔改走原有 P2 上游，不会把一笔订单拆成两种来源。其他备注或空备注的卡密不会被当作 P1 使用。

给 `extra.provider` 配置两条按顺序匹配的规则：`card.notes` 等于 `p1` 时输出 `p1`；`source.id` 等于 P2 站点连接的 ID 时输出 `p2`；“否则输出”留空。这样未知来源会被 AI Top-up 拒绝，避免误入另一渠道。`extra.category` 仍需按商品选择 AI Top-up 支持的套餐，例如 Go 新开通为 `new_activation_go`。AI Top-up 当前不支持 Codex 额度转换，勿把 Codex 额度商品绑定到它。

当前店铺的 AI Top-up 对应关系：GPT Plus 为 `new_activation_plus`，GPT 20x 为 `new_activation_pro_20x`，GPT Pro 5x 为 `new_activation_pro_5x`，GPT Go 为 `new_activation_go`。导入前须确认上游卡密的实际套餐与商品一致；AI Top-up 会验证套餐，不一致时保留订单等待处理。

新建的自动发卡商品可按批次备注 `p1`、`p2`、`p3` 分别导入库存，并给 `extra.provider` 配置三条 `card.notes` 精确匹配规则；“否则输出”留空。AI Top-up 可生成与商城 Go、Plus、Pro 5X、Pro 10X、Pro Max 25X 对应的 P3 系统卡，历史 Pro 20X 类型只供旧卡兼容，不能混入 10X 或 25X 商品。已生成的系统卡直接导入对应商品，开启“已是系统卡密”，无需调用转换器。系统卡生成时不占用上游库存；正式销售前还要确认 AI Top-up 有同渠道、同类型的可分配上游卡，否则买家兑换时会收到缺货提示。没有导入卡密时，自动发卡商品显示缺货。

商品配置了绑定后，未标记“已是系统卡密”的库存及上游原始卡密会先调用转换器；导入时已标记的系统卡密直接交付。同一订单混用两类卡密时，只转换原始卡密并保留交付顺序。未配置绑定的商品始终按原有流程交付。管理员手动发货时，如果输入的是逐行卡密且数量与订单一致，也会调用转换器；上游返回的人工处理说明不会被当作卡密转换。转换结果是买家页面、下游供货接口、邮件和 Webhook 共用的正式交付内容。

## 失败与恢复

转换器调用失败时，订单保持处理中，不会把上游卡密交给买家。上游采购已经成功时，系统会保存其原始交付供内部重试，后续只重试转换，不会再次向上游采购。本地库存商品会固定本次使用的卡密；重试不会再扣另一批库存。

健康任务每分钟检查启用中的转换器。连续探测失败达到阈值会记录事件并通知管理员 Telegram；恢复时会记录恢复事件并唤醒挂起转换。全部卡密转换成功后，系统才完成订单并通知买家。类型错误、幂等冲突或修复配置后仍失败的订单，可在采购单页面使用“重试卡密转换”，此操作不会重新采购。后台首页会显示异常转换器名称、最近错误和影响商品数；转换事件日志不记录 Token 或卡密明文。

协议、健康探测和订单恢复的开发细节见[协议文档](./card-converter-protocol)。

若从旧请求结构升级，需同时更新 Zebra Store 和转换程序，并先核对待转换订单；旧结构产生的幂等记录可能与新请求内容不一致，不能直接按新结构重放。
